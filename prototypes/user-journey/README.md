# CEPM 用户旅程原型（已采纳 A，调整版供确认）

这是一次性 HTML 交互原型，不是生产 GUI。正式实现暂停，待用户确认方向后再更新实现规格。所有扩展、版本、CLI、文件操作和浏览器观测都是模拟数据；扩展操作在刷新后重置，置顶和上次选择单独保存。页面只读取用户在演示中填写的文本，不获取远程产物、不读取本地目录。

## 运行

直接双击 `index.html`，或在仓库根目录运行：

```sh
python3 -m http.server 8766 --bind 127.0.0.1 --directory prototypes/user-journey
```

打开 http://127.0.0.1:8766/?variant=A 。无需安装依赖或构建。

## 要回答的设计问题

用户能否从当前状态知道下一步该做什么，并走通从首次添加到日常更新、处理失败的旅程？

三个结构方向共用交互状态：

- A 扩展库：侧边导航、扩展列表、按需打开详情。适合日常维护，建议作为讨论起点。
- B 待办首页：先呈现需要用户完成的事项，再呈现扩展库。优先回答“今天要做什么”。
- C 紧凑列表：左侧选择扩展、右侧常驻详情，适合持续操作单个扩展。

底部箭头 / 键盘左右键切换 `?variant=A|B|C`。输入时不劫持方向键。底部工具条仅用于比较原型，不属于正式应用。

## 建议体验路径

1. 选择“首次使用” → 添加扩展 → 选择来源（Release / 仓库子目录 / 本地文件夹）→ 预览产物 → 选择浏览器配置 → 文件准备 → 首次加载三步指引 → 核对。
2. 选择“日常管理” → 更新 OpenCLI → 确认更新 → 重载指引 → 输入浏览器显示版本并勾选 → 回到用户已确认状态。
3. 在重载引导选择“稍后完成”，稍后从待办继续；详情保留历史确认版本，不把文件版本当成生效版本。
4. 更新后打开详情 → 报告加载失败 → 确认已实际重载且失败 → 恢复旧文件 → 重新核对。
5. 选择“批量部分失败” → 查看全部更新 → 更新 → 看独立成功/失败结果；失败项保留旧版，成功项等待重载。
6. 选择“同版本内容变化” → 明确选择重新部署；也可从详情选择旧版体验降级确认。仓库/本地旧版要求另给 ref/目录，不虚构历史来源。

演示首次加载时，版本填弹窗显示值；扩展 ID 可填 32 个小写 `a`。OpenCLI 版本号为示例，不代表真实发行版本。

## 设计边界

- 首页只放用户需要判断的状态和操作，目录、ID、具体提交折叠到详情。
- 文件部署完成与浏览器确认分开；未完成不会消失，可以稍后继续。
- 正式版仍使用 Rust + GPUI；HTML 只是交互与视觉确认工具。
- 2026-10-29 用户已采纳 A；后续布局调整和原生页面交接仍以原型确认，代码不直接进入生产。

## 实际检查

已通过 macOS Chrome 手动点击检查 A/B/C 布局切换、空白状态、Release 添加向导、更新核对闭环、批量一成功一失败、明确加载失败后的文件恢复与再次核对。这里只验证原型交互，不作为 Rust 安装能力或浏览器持久性验收。

## 第二轮：浏览器 / Profile 是顶层操作范围

用户提出先切换具体浏览器和 Profile，再显示扩展。原型已按此方向调整，A/B/C 共用同一个顶层两级切换器；完整视觉仍待确认。

- 顶层：Chrome / Edge → 该浏览器的具体 Profile → 仅此配置中的安装。
- 添加直接继承当前目标；向导最后确认绑定位置，不再让用户自由填写一个无法定位的配置名称。
- 检查、批量更新、数量、待办和操作记录全部限定当前 Profile，不提供跨配置“全部更新”。
- 同一个 OpenCLI 在 Chrome 个人中为 1.2.0，在 Chrome 工作中为 1.1.0，各自拥有独立安装目录、版本、备份与确认状态。
- 每条安装通过 targetId 关联目标。正式实现拟以浏览器实例、用户数据目录和 Profile 目录绑定实际目标，显示名仅用于识别。配置位置核验不等于扩展已生效。
- 顶部“配置位置与识别”展示绑定并给出手动定位入口。原型没有扫描本机，也没有真实启动指定 Profile。
- “目标配置找不到”场景保留安装记录与文件、暂停维护；不会静默改用默认 Profile。无法证明是原配置时，正式实现应要求重新绑定并重新核对，不能继承旧确认。
- 此处不增加一次安装到多个配置、自动迁移或共享可变安装文件的功能。

已在 Chrome 中检查：个人配置只显示 2 条记录；切换工作配置显示其 3 条记录，同名 OpenCLI 版本仍为 1.1.0；绑定详情显示工作配置的独立目录。正式实现继续暂停。


## 第三轮：采纳 A，侧栏快速切换与浏览器原生管理

用户已采纳 A，要求浏览器与配置选择压缩到左侧菜单顶部。当前 A 用一个“Chrome · 个人”按钮展开分组菜单，切换后列表与操作范围同步变化。B/C 留作历史比较，不再是首页的待选方向。

新增侧栏“打开浏览器扩展管理页”、详情“在浏览器中管理”和加载/重载指引入口。交接目标始终来自安装绑定的浏览器和 Profile。当前纯 HTML 仅模拟交接，不启动真实浏览器、不宣称能够操控内部页面。

正式实现的建议边界：

- CEPM 负责来源、产物、版本、备份与恢复；浏览器页面保留其原生加载、重载、启停、权限和移除交互。
- 使用绑定的浏览器应用、用户数据目录和 Profile 目录请求打开管理页，不能把裸 URL 交给系统默认浏览器而丢失目标配置。指定 Profile 的实际路由需在后续 macOS Chrome 实现中验证；不增加 Windows/Edge 验证门槛。
- 打开页面/进程调用成功不等于正确 Profile 中的扩展已加载；保留返回 CEPM 后的核对步骤。
- 不在 HTML / WebView 中嵌入原生管理页，不把它当公共 DOM/API。应用代点、自动读取状态仍是单独能力验证问题，尚未承诺或实现。

依据：Chromium 的 [用户数据目录文档](https://chromium.googlesource.com/chromium/src.git/+/HEAD/docs/user_data_dir.md)、[profile-directory 参数声明](https://github.com/chromium/chromium/blob/main/chrome/common/chrome_switches.h)、[内部页面保护说明](https://chromium.googlesource.com/chromium/src/+/main/extensions/docs/security_faq.md)。Chrome [远程调试限制](https://developer.chrome.com/blog/remote-debugging-port?hl=en)也说明不能假定任意日常 Profile 均可直接通过调试接口接管。

实际检查：A 顶部不再出现两行选择栏；侧栏菜单能从个人切至工作；原生管理入口提示对应工作配置且不改变版本或确认状态。修复了原型操作分支内变量遮蔽对目标配置函数的影响。


## 第四轮：多个置顶与上次选择

用户明确要求：常用浏览器配置可同时置顶多个，每次打开恢复最后选中的 Profile。

- 菜单顶部展示“置顶”分组，条目携带浏览器名避免同名 Profile 混淆；其余配置继续按浏览器分组，不重复显示置顶项。
- 点击 ☆ / ★ 置顶或取消置顶，不改变当前配置，不影响安装。置顶顺序按加入顺序，不增加拖拽排序功能。
- 选择后保存该配置的稳定内部 ID，再次打开自动恢复；不以显示名称匹配。历史目标不存在时保留“上次配置（不可用）”入口，要求定位，不静默切到默认配置。
- 这一轮正是在验证偏好持久性，因此原型有意用 localStorage 保存 `cepm-journey-prototype-preferences-v1`，仅含置顶 ID 与最后目标标识；不保存扩展部署或浏览器状态。正式应用将使用本机应用设置。
- 重新打开需在同一浏览器配置、同一原型地址；HTML 文件与 localhost 属于不同存储范围。原型场景“重置”会选择其演示目标并更新最后选择，但不清除置顶。

实际点击验证：同时置顶 Chrome 个人与工作，切换工作后重新加载；当前工作配置及两个置顶均保留。正式功能尚未实现。
