# 本地目录版本声明：事实与建议

核查日期：2026-10-29。用户已确认本地目录需要约定的版本声明；以下具体方案仍待访谈确认。

后续访谈结论：已采纳 `manifest.json.version`、复制到固定安装目录、同版本内容变化须明确重新部署；已确认首版允许用户选择可获取的任意有效版本，包括主动降级。以下保留原调研内容，当前决策以 PRD 为准。

## 官方约定

Chrome 扩展以扩展根目录的 `manifest.json` 描述扩展，其 `version` 是一至四段数字，每段 0–65535，非零段不能有前导零，整体不能全为零。按数字段比较版本，缺失段按零处理；因此 `1.2` 与 `1.2.0` 相等，`1.10` 大于 `1.9`。`version_name` 为可选展示名称，不应承担排序或更新判断。[Chrome 官方版本规范](https://developer.chrome.com/docs/extensions/reference/manifest/version)

扩展根目录必须含 `manifest.json`；Chrome 官方入门示例直接加载该目录。清单、service worker 和内容脚本的变化需要重载（内容脚本还涉及相应网页），仅更新目录不证明浏览器已生效。[Chrome 官方加载与重载说明](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world)

## 建议的 CEPM 契约（未定案）

- 本地来源选择可直接加载的构建产物目录，以其 `manifest.json.version` 为唯一扩展版本声明，不要求额外的 CEPM 专用版本文件。
- 展示名称可采用 `version_name`，同时保留机器比较使用的 `version`。
- `package.json.version`、仓库 tag、目录名均不替代扩展版本；这些可能属于其他组件或源码工程。
- 安装时校验包结构、声明和引用文件；只有 manifest 存在并不能证明源码目录已经构建完成。
- 版本变大时提供更新；版本相同、文件内容变化时显示“同版本内容变化”，让用户明确选择重新部署，不能静默视为无变化或偷偷覆盖；版本降低时按降级请求处理，不视为普通更新。
- 内容指纹与版本号承担不同用途：前者识别文件变化，后者表达作者声明的版本顺序。
- 建议复制到管理器固定安装目录，使来源目录移动或删除不破坏现有安装；用户尚未确认复制模式，不将其视为决策。

## 尚需用户决定

1. 是否采纳原生 manifest 版本约定。
2. 同版本内容变化是否允许显式重新部署，以及首版是否允许显式降级。
3. 是否采用来源目录与安装目录分离的复制模式。

## 证据边界

上述版本排序是 Chrome 扩展版本规则，不是完整 SemVer；浏览器商店的自动更新机制不能直接推导出本地已解压安装会自动重载或升级。
